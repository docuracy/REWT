## General

None of the examples given here should be fixed with a one-off targeted fix, but rather by a general rule that should be applied across the network. For clarity, we should have a canonical machine+human-readable ordered list of rules.

- My specification of the sea network was probably mistaken, as a great many sea entries (for example os:node/891FB238-57E0-4AA3-A7BE-AA74D38E42C6) lie a long distance from the sea network. A better specification might simply be the OS Mean High Water lines: streams which cross it should be truncated and connected, those which lie entirely below it should be dropped from the network. This should be done before any synthetic connectors are added.
- With the existing sea network, sea entry termini like os:node/58209E4B-B9F4-4B42-865A-1EC8EBD44DD6, which are within a threshold distance of a sea network node should be connected it. Blocked sea entries like os:node/5E6F05F4-CAFE-41C6-BEB9-1B161A959477 may need a longer threshold.
- Not all crossings that do not join are being marked as such, for example os:link/D29D6029-4B22-4A33-9344-061FEB12395A and rewt:link/699fb26d7d27. A tool should exist to enable toggling them in the viewer.
- What should be a node at easting 396919.51 northing 161634.75 has been incorrectly marked as a corroborated non-join on account of a C&RT culvert nearby. This is a bad failure mode.
- I see no reason why os:link/0F4CE6CA-CC2E-40DB-84E4-C02F66B2F360 is barred from connecting to os:link/6CEF7E5F-4E86-49E9-A2D3-4686EF417FA6: the node is marked as a non-join (uncorroborated).
- I wonder if we should be making the higher-resolution DEM work harder rather than relying on the lower-resolution one and OS flow-direction metadata. WHG uses the terrarium tileserver DEM on https://s3.amazonaws.com/elevation-tiles-prod/terrarium/<z>/<x>/<y>.png, which could be decoded for point height at z15 (its maximum): if used they should be cached; a national sweep of nodes in England and Wales might be a very useful pre-processing step, as the primary indicator of flow direction (or ambiguity) in a link.
- We seem to have water polygon gaps which were solved in "Premodern Rivers" by skeletonisation of OS water polygons: are we still ding this? One such gap is between os:node/60DBE0AE-0DCD-4ECB-87D5-B977071B2F79 and os:link/43C14AFB-1529-4F95-8A97-F47D37D36005. Another lies west of os:node/A4A65229-861B-4F05-9752-2E23ECCFDA35, but this is marked as a sea entry so should presumably be picked up by the MHW line if we set that as the sea network.



- clickable nodes should show in their popups expandable details of any attached links. At present a click opens a node overlay and a single link overlay, sometimes colliding, even when there are two connected links (example: os:node/7D63F86E-1FBE-4AC3-AEFE-B28073CDAF05)
- A link or node showing a popup should be styled with a highlight (maybe a yellow halo?), or when hovered above a practical zoom threshold.
- A dead end node with just two inflows on a canal is suspect - one should probably be an outflow, especially if one has a disagreeing screening_terrain_verdict (example: os:node/7D63F86E-1FBE-4AC3-AEFE-B28073CDAF05)
- If extending a link past a dead end node passes within a threshold distance of an unconnected end of another link, and if the two links are aligned within an angular threshold, there's a high possibility that they should be connected (example: os:node/E4B75286-CF0D-4FC4-A0A6-1C597D17720A)
